# Focus v0.2 架构纰漏详细分析与修复方案

> 基于 `feat-v0.2-release`（commit `34cde72`）的深度代码审查。

---

## 一、总体评估

| 维度 | 评分（1-5） | 一句话概括 |
|------|-------------|-----------|
| 消息循环与响应性 | ⭐⭐ | `Update` 过于庞大，`syncWorktreeActivities` 在主线程全量重建缓存 |
| 路由与可扩展性 | ⭐⭐ | 硬编码 pane ID 列表，循环引用（Model↔Orchestrator） |
| 状态管理 | ⭐⭐⭐ | 过度集中，但无数据竞争；缓存非增量 |
| 事件/命令耦合 | ⭐⭐ | SQLite 下 EventBus 缺失导致 Orchestrator 不工作；dual-write 不一致 |
| 存储并发安全 | ⭐⭐⭐ | 依赖 `database/sql`，无 busy_timeout；缺少事务封装 |
| MCP/A2A/Agent 边界 | ⭐⭐ | A2A 未按架构废弃；Registry 无锁；MCP handler 阻塞 |
| 内存/Goroutine 安全 | ⭐⭐ | shell VT pipe、MCP accept loop、Trellis fire-and-forget 均有泄漏风险 |
| 面板生命周期 | ⭐⭐⭐ | 基本正确，但 overlay 优先级硬编码，quit 时清理不完整 |

## 二、纰漏 1：消息循环主线程阻塞

### 2.1 问题位置
- `internal/app/app.go:1646~2422` — `Update` 方法（>800 行，40+ 个 `case`）
- `internal/app/app.go:4953~5232` — `syncWorktreeActivities` / `refreshResumeSummaryCache`
- `internal/app/piggyback.go:43` — `piggybackForParams`

### 2.2 会导致什么具体问题

**（1）UI 帧率暴跌与输入延迟**

Bubble Tea 的 `Update` 必须在**主 goroutine 同步执行**。`syncWorktreeActivities` 每次触发时都会：

1. 调用 `ListWorktreeContexts`、`ListTaskContexts`、`ListAgentSessions`、`ListTaskPlans` 等多次数据库查询
2. 遍历所有 Worktree × Task × Plan × Step，全量重建 `resumeSummaryCache`
3. 调用 `DiscoverRunningAgents()` 执行外部 `pgrep` 进程扫描

当项目规模达到 **50 个 worktree + 100 个 task + 20 个 plan** 时，这个函数的耗时可能达到 **100~500ms**。在此期间：
- 键盘按键事件被缓冲，用户感受到明显的输入延迟
- 鼠标滚轮/点击事件可能丢失（Bubble Tea 的鼠标事件是同步投递的，如果 Update 被阻塞，后续事件可能合并或丢弃）
- 帧率从 60fps 暴跌到 2fps，界面看起来像"卡住"

**（2）MCP Tool 调用阻塞其他 Agent**

`piggybackForParams` 在 MCP tool handler 的调用路径上**同步查询 EventStore**，设置了 500ms 超时。如果 EventStore 查询变慢（如 PostgreSQL 模式下连接池耗尽），整个 MCP handler 会阻塞 `Update` 循环，导致同一会话的其他 tool call 全部排队等待。

**（3）无法扩展**

每新增一个消息类型，都需要在 `Update` 的巨型 switch 中添加 case。当前 `app.go` 已超过 6200 行，编译时间、IDE 索引时间、代码审查时间都在线性增长。未来增加"全局搜索面板"、"配置编辑器"等新功能时，这个文件会膨胀到不可维护。

### 2.3 修复方案

**方案 A：将耗时操作移出主线程（推荐，改动小，见效快）**

把 `syncWorktreeActivities` 的**查询部分**放到后台 goroutine，通过 channel 将结果传回主循环：

```go
// 新增消息类型
type worktreeActivitiesSyncedMsg struct {
    cache map[string]gitmodel.WorktreeResumeSummary
    sessions []*agents.Session
}

func (m model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
    switch msg := msg.(type) {
    // ...
    case worktreeActivitiesSyncedMsg:
        m.resumeSummaryCache = msg.cache
        // 更新 pane 状态
        m.invalidateView()
        return m, nil
    }
}

func (m *model) syncWorktreeActivities() tea.Cmd {
    return func() tea.Msg {
        // 所有查询在后台 goroutine 执行
        persisted := m.persistedAgentSessions()
        persisted = m.reconcileDiscoveredAgentSessions(persisted, agents.DiscoverRunningAgents())
        cache := m.buildResumeSummaryCache(persisted) // 提取为纯函数
        return worktreeActivitiesSyncedMsg{cache: cache, sessions: persisted}
    }
}
```

> Bubble Tea 的 `tea.Cmd` 返回值会自动在主循环中投递为 `tea.Msg`，所以这是框架推荐的模式。

**方案 B：增量更新缓存（长期优化）**

当前 `refreshResumeSummaryCache` 是**全量清空后重建**。改为事件驱动增量更新：

```go
func (m *model) handleEvent(e events.Event) {
    switch e.EventType {
    case events.WorktreeContextUpdated:
        m.resumeSummaryCache.UpdateWorktree(e.AggregateID)
    case events.AgentSessionHeartbeat:
        m.resumeSummaryCache.UpdateAgent(e.AggregateID)
    case events.TaskStateChanged:
        m.resumeSummaryCache.UpdateTask(e.AggregateID)
    }
}
```

这样只有在相关数据变化时才更新对应条目，时间复杂度从 O(N×M) 降到 O(1)。

**方案 C：子类型分派（长期重构）**

将 `Update` 按子系统拆分为多个 handler：

```go
func (m model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
    switch msg := msg.(type) {
    case tea.KeyPressMsg:
        return m.handleKey(msg)
    case tea.MouseMsg:
        return m.handleMouse(msg)
    }
    
    // 按子系统分派
    if m, cmd := m.gitHandler.Update(msg); cmd != nil { return m, cmd }
    if m, cmd := m.agentHandler.Update(msg); cmd != nil { return m, cmd }
    if m, cmd := m.dagHandler.Update(msg); cmd != nil { return m, cmd }
    
    return m, nil
}
```

> 这类似于 Go 的 http.ServeMux 模式，每个子系统维护自己的消息路由表。

**方案 D：piggybackForParams 异步化**

`piggybackForParams` 改为读取内存缓存而非同步查询 EventStore：

```go
// 在 model 中维护一个 projectionCache，由 ProjectionBuilder 异步更新
func (m *model) piggybackForParams(ctx context.Context) (map[string]any, error) {
    return m.projectionCache.Snapshot(), nil // O(1)，无阻塞
}
```

## 三、纰漏 2：Orchestrator 在 SQLite 下完全失效

### 3.1 问题位置
- `internal/store/db.go:75` — `newSQLiteStore` 不创建 `EventBus`
- `internal/app/app.go:295` — `if bus := store.EventBus(); bus != nil { m.orch = orchestrator.New(...) }`
- `internal/store/db.go:173` — `EventBus()` 直接返回 `s.bus`（SQLite 下为 `nil`）

### 3.2 会导致什么具体问题

**（1）核心规则引擎在默认模式下不存在**

Focus 的默认模式是 SQLite（没有设置 `FOCUS_STORE=postgresql` 时）。在此模式下：

```go
// newSQLiteStore 返回的 Store
s := &Store{db: db, mode: "sqlite"}  // bus = nil

// app.go 初始化
if bus := store.EventBus(); bus != nil {
    m.orch = orchestrator.New(...)  // 永远不会执行
}
```

这意味着 **Orchestrator 完全不启动**。但架构文档和 ADR 明确声明 Orchestrator 是"常驻 goroutine，消费领域事件并执行工作流规则"。

**（2）任务阻塞检测失效**

Orchestrator 的 `eventLoop` 监听 `TaskStateChanged` 事件，当任务变为 `done` 时检查下游任务的前置条件。如果 Orchestrator 不存在：
- 用户将任务 A 标记为 `done`
- 任务 B 的前置条件已经满足，但不会自动变为 `active`
- 用户必须手动检查并更新每个下游任务的状态
- 在 20+ 个任务的 DAG 中，这会成为严重的操作负担

**（3）Agent 心跳超时无人处理**

Orchestrator 的 `heartbeatLoop` 每 30 秒检查一次 AgentSession 的最后心跳时间。如果超时会：
- 调用 `MarkSessionDisconnected` 更新数据库状态
- 发送 `heartbeat_timeout` notification 提醒用户

如果 Orchestrator 不存在，Agent 进程崩溃或网络断开后，TUI 上该 session 永远显示为 `running`，用户无法知道 Agent 已经失联。

**（4）计划完成检测失效**

当 Plan 的所有 Step 都完成时，Orchestrator 应该发送 `plan_completed` notification。缺失此功能意味着用户需要手动检查每个 plan 的进度。

### 3.3 修复方案

**方案 A：SQLite 下也创建 EventBus（推荐，1 行改动）**

```go
func newSQLiteStore(dbPath string) (*Store, error) {
    // ... 现有代码 ...
    s := &Store{
        db:   db,
        mode: "sqlite",
        bus:  events.NewEventBus(), // 新增：所有模式都有 EventBus
    }
    // ...
}
```

> 影响：SQLite 模式下 EventBus 是纯内存的，不持久化。但这足够了，因为 Orchestrator 只消费事件，不需要事件持久化（那是 EventStore 的职责）。

**方案 B：统一 Store 构造函数（更干净）**

将 `newSQLiteStore` 和 `newPostgresStore` 的公共部分提取出来：

```go
func New(dbPath string) (*Store, error) {
    mode := os.Getenv("FOCUS_STORE")
    if mode == "" { mode = "sqlite" }
    
    var db *sql.DB
    var pool *pgxpool.Pool
    // ... 根据 mode 初始化 db/pool ...
    
    bus := events.NewEventBus()  // 所有模式统一创建
    s := &Store{db: db, pgPool: pool, bus: bus, mode: mode}
    // ...
}
```

**验证步骤**：
1. 启动 Focus（不设置 `FOCUS_STORE`）
2. 创建一个带 dependency 的 DAG
3. 将上游任务标记为 `done`
4. 验证下游任务自动变为 `active`（Orchestrator 在工作）

## 四、纰漏 3：Goroutine 泄漏（三重泄漏点）

### 4.1 问题位置

**泄漏点 A：Shell VT Pipe Drain**
- `internal/ui/shell/shell.go:109`：`go io.Copy(p, vtm)`

**泄漏点 B：Shell AutoType**
- `internal/ui/shell/shell.go:136`：`go func() { time.Sleep(200ms); m.pty.Write(...) }()`

**泄漏点 C：MCP Accept Loop**
- `internal/mcp/server.go:270`：`go s.handleConn(conn)`
- `internal/mcp/server.go:281`：`decoder.Decode(&req)` 可能永久阻塞

**泄漏点 D：Trellis Fire-and-Forget**
- `internal/app/app.go:6200`：`syncTaskCreateToTrellis` 启动无 context 的 goroutine
- `internal/app/app.go:6221`：`syncTaskStateToTrellis` 同理

### 4.2 会导致什么具体问题

**（1）Shell Pane 泄漏（最常见）**

每次打开一个 shell pane：
1. `startShell()` 启动 `io.Copy` goroutine（泄漏点 A）
2. 如果配置了 `autoType`，再启动一个 sleep-then-write goroutine（泄漏点 B）
3. 用户关闭 pane 时，`m.pty = nil`，但 `io.Copy` 仍在 `vtm` 的 pipe 读取端阻塞
4. `autoType` goroutine 在 200ms 后尝试向已关闭的 PTY 写入

**实测估算**：
- 用户每天打开/关闭 30 次 shell pane
- 每次泄漏 1~2 个 goroutine
- 一周后 goroutine 数从 50 增长到 260+
- 每个 goroutine 栈 2KB，额外内存约 400KB（不大，但 goroutine 调度开销累积）
- 更严重的是：这些 goroutine 持有的 `vtm` 和 `p` 对象不会被 GC，因为 goroutine 还在引用它们

**（2）MCP 连接泄漏**

MCP Server 的 Unix Socket accept loop：
```go
func (s *Server) acceptLoop(listener net.Listener) {
    for {
        conn, _ := listener.Accept()
        go s.handleConn(conn)  // 每个连接一个 goroutine
    }
}

func (s *Server) handleConn(conn net.Conn) {
    decoder := json.NewDecoder(conn)
    for {
        var req JSONRPCRequest
        if err := decoder.Decode(&req); err != nil {  // 如果客户端不关闭连接，这里永远阻塞
            return
        }
    }
}
```

如果 MCP 客户端（如 Claude Code）建立长连接后崩溃或不发送 EOF，`handleConn` 中的 `json.NewDecoder(conn).Decode` 会**永久阻塞在 `conn.Read` 上**。

**实测估算**：
- 每个 Agent 会话建立 1 个 MCP 连接
- 如果 Agent 异常退出而不关闭连接（常见情况）
- 每个泄漏的 goroutine 持有 `conn` 对象
- 100 次异常退出后，100 个 goroutine 永久阻塞

**（3）Trellis 同步泄漏**

```go
func (m *model) syncTaskCreateToTrellis(taskID string) {
    go func() {
        // 调用 trellisBridge.SyncTaskCreate
        // 如果 trellis 脚本卡住（如网络挂载的目录），这个 goroutine 永远阻塞
    }()
}
```

如果 `.trellis/scripts/task.py` 因为某种原因卡住（如等待用户输入、网络超时），这个 goroutine 永远不会返回。

### 4.3 修复方案

**修复 A：Shell VT Pipe Drain（推荐）**

```go
type Model struct {
    // ...
    ctx    context.Context
    cancel context.CancelFunc
}

func (m *Model) startShell() tea.Cmd {
    return func() tea.Msg {
        // ...
        m.ctx, m.cancel = context.WithCancel(context.Background())
        
        go func() {
            // 使用 context 控制退出
            done := make(chan struct{})
            go func() {
                io.Copy(p, vtm)
                close(done)
            }()
            select {
            case <-done:
            case <-m.ctx.Done():
            }
        }()
        // ...
    }
}

func (m *Model) Close() {
    if m.cancel != nil {
        m.cancel()
    }
    if m.pty != nil {
        m.pty.Close()
    }
}
```

**修复 B：Shell AutoType**

```go
if m.autoType != "" {
    go func() {
        select {
        case <-time.After(200 * time.Millisecond):
        case <-m.ctx.Done():
            return
        }
        if m.pty != nil && m.running {
            m.pty.Write([]byte(m.autoType + "\r"))
        }
    }()
}
```

**修复 C：MCP HandleConn 超时**

```go
func (s *Server) handleConn(conn net.Conn) {
    defer s.wg.Done()
    defer func() { _ = conn.Close() }()
    
    // 设置读超时
    if tcpConn, ok := conn.(*net.TCPConn); ok {
        tcpConn.SetKeepAlive(true)
        tcpConn.SetKeepAlivePeriod(30 * time.Second)
    }
    
    decoder := json.NewDecoder(conn)
    encoder := json.NewEncoder(conn)
    
    for {
        // 使用 SetReadDeadline 实现超时
        if deadlineConn, ok := conn.(interface{ SetReadDeadline(time.Time) error }); ok {
            deadlineConn.SetReadDeadline(time.Now().Add(5 * time.Minute))
        }
        
        var req JSONRPCRequest
        if err := decoder.Decode(&req); err != nil {
            if errors.Is(err, io.EOF) || errors.Is(err, net.ErrClosed) {
                return
            }
            // 其他错误也关闭连接
            return
        }
        // ...
    }
}
```

**修复 D：Trellis Sync 超时**


## 五、纰漏 4：路由硬编码与循环引用

### 5.1 问题位置
- `internal/app/page.go:511~583` — `activeOverlayPane()` 硬编码 20+ pane ID 的 if-else 链
- `internal/app/page.go:585~593` — `isOverlayPane()` 超长单行布尔条件
- `internal/app/app.go:4456` — `appOrchestratorStore{model: &m}` 内嵌 `*model`
- `internal/app/app.go:4568` — `protocolOrchestratorLauncher`

### 5.2 会导致什么具体问题

**（1）新增 Overlay 极易出错**

假设要新增一个 `paneAgentConfig`（Agent 配置面板）：

1. 在 `activeOverlayPane()` 中找到正确的插入位置（优先级顺序）
2. 在 `isOverlayPane()` 的布尔条件中添加 `|| id == paneAgentConfig`
3. 在 `handleKey()` 的快捷键分发中添加对新 pane 的处理
4. 在 `legacyOverlayBindings` 中添加键位绑定
5. 在 `closeShellPanes()` 中确保退出时关闭

**遗漏任何一步都会导致 bug**：
- 如果忘记在 `activeOverlayPane()` 中添加，新 pane 会被底层 overlay 遮挡
- 如果忘记在 `isOverlayPane()` 中添加，键盘事件会被错误路由到底层 pane
- 如果忘记在 `handleKey()` 中添加，`esc` 键可能无法关闭新 pane

**（2）循环引用导致测试困难**

```go
type appOrchestratorStore struct {
    model *model  // 直接内嵌整个 TUI Model
}
```

这形成了 **TUI Model → Orchestrator → appOrchestratorStore → TUI Model** 的循环引用。后果：
- 无法单独测试 Orchestrator（需要构造完整的 TUI Model）
- TUI Model 的生命周期与 Orchestrator 强耦合：TUI 退出时必须手动停止 Orchestrator，否则 `model` 对象被 Orchestrator 引用无法 GC
- `appOrchestratorStore` 实现了 `orchestrator.Store` 接口，但接口方法的实现依赖 `model` 的 20+ 个字段，任何字段改名都会破坏 Orchestrator

**（3）协议层与 UI 层耦合**

```go
type protocolOrchestratorLauncher struct {
    m *model
}
```

MCP Server 的 tool handler 调用 `LaunchTask` 时，直接操作 TUI Model。这意味着：
- MCP Server 的 HTTP handler 在主 goroutine 中执行 tool call
- tool call 触发 `LaunchTask` → 修改 TUI Model → 可能触发 pane 切换
- 如果 MCP 同时收到多个 tool call，它们会竞争修改 Model

### 5.3 修复方案

**修复 A：声明式 Pane 注册表（推荐）**

```go
// internal/app/pane_registry.go

type PaneRegistration struct {
    ID       models.PaneID
    Type     models.PaneType
    ZIndex   int           // overlay 优先级，数字越大越上层
    IsOverlay bool
    Bindings func() []models.KeyBinding
}

type PaneRegistry struct {
    panes map[models.PaneID]PaneRegistration
}

func (r *PaneRegistry) Register(p PaneRegistration) {
    r.panes[p.ID] = p
}

func (r *PaneRegistry) ActiveOverlay(paneMeta map[models.PaneID]models.PaneMeta) models.PaneID {
    var best models.PaneID
    var bestZ int = -1
    for id, reg := range r.panes {
        if !reg.IsOverlay { continue }
        if _, ok := paneMeta[id]; !ok { continue }
        if reg.ZIndex > bestZ {
            bestZ = reg.ZIndex
            best = id
        }
    }
    return best
}

func (r *PaneRegistry) IsOverlay(id models.PaneID) bool {
    if reg, ok := r.panes[id]; ok {
        return reg.IsOverlay
    }
    return false
}
```

使用时：
```go
registry := NewPaneRegistry()
registry.Register(PaneRegistration{ID: paneHelpOverlay, Type: models.PaneTypeOverlay, ZIndex: 100})
registry.Register(PaneRegistration{ID: paneTodoOverlay, Type: models.PaneTypeOverlay, ZIndex: 90})
registry.Register(PaneRegistration{ID: paneAgentConfig, Type: models.PaneTypeOverlay, ZIndex: 50}) // 新增只需一行
```

**修复 B：解除循环引用**

```go

```

在 `model.New()` 中初始化：


**修复 C：MCP Tool Handler 异步化**


## 六、纰漏 5：事件丢弃无感知

### 6.1 问题位置
- `internal/events/bus.go:57~71` — `Publish` 方法

### 6.2 会导致什么具体问题

**代码**：
```go
func (eb *EventBus) Publish(e Event) {
    eb.mu.RLock()
    defer eb.mu.RUnlock()
    for _, subs := range eb.subscribers {
        for _, sub := range subs {
            if sub.filter != nil && !sub.filter(e) {
                continue
            }
            select {
            case sub.ch <- e:
            default:
                // channel full, drop event for this subscriber
            }
        }
    }
}
```

**（1）Orchestrator 丢失关键事件**

Orchestrator 订阅了 `TaskStateChanged` 事件。当用户快速连续更新多个任务状态时（如批量标记完成），如果 Orchestrator 的 channel（缓冲 64）被填满，后续事件被静默丢弃。

后果：
- 任务 A 变为 `done` → Orchestrator 处理 → 下游任务 B 变为 `ready`
- 任务 C 变为 `done` → 事件被丢弃 → Orchestrator 不知道 → 下游任务 D 永远不会变为 `ready`
- 用户看到"为什么 D 还是 blocked？A 和 C 都已经 done 了"

**（2）ProjectionBuilder 视图不一致**

ProjectionBuilder 消费事件来更新查询视图。如果事件被丢弃：
- SQLite 投影表中的数据与 PostgreSQL EventStore 不一致
- `ListWorktreeContexts` 返回的结果缺少最新变更
- 用户看到的 worktree 列表与实际情况不符

**（3）调试噩梦**

事件丢弃是**静默的**——没有任何日志、没有任何指标、没有任何错误提示。当系统出现不一致时，开发者需要：
1. 怀疑是事件丢弃
2. 在 `bus.go` 中添加调试日志
3. 重现问题
4. 确认是 channel 满导致的丢弃

这个过程可能需要数小时甚至数天。

### 6.3 修复方案

**方案 A：丢弃时记录日志（最小改动）**

```go
case sub.ch <- e:
default:
    log.Printf("[event-bus] dropped event %s for subscriber %s (channel full)", e.EventType, subscriberID)
}
```

> 但这需要 `Publish` 知道 subscriberID，当前循环中 subscriberID 是 `range` 的键。

**方案 B：增大缓冲 + 背压通知**

```go
const eventBusBufferSize = 256 // 从 64 增大

func (eb *EventBus) Publish(e Event) {
    // ...
    select {
    case sub.ch <- e:
    default:
        // 尝试非阻塞发送，如果失败则记录
        eb.dropCount[subscriberID]++
    }
}
```

**方案 C：阻塞发送（不推荐，但彻底）**

```go
case sub.ch <- e:
default:
    // 阻塞等待，直到消费者处理完
    sub.ch <- e
}
```

> 这会阻塞 `Publish` 的调用者（可能是主 goroutine），导致 TUI 卡顿。不推荐。

**方案 D：为关键消费者提供专用大缓冲 channel**

```go
func (eb *EventBus) SubscribeCritical(subscriberID string, filter EventFilter) <-chan Event {
    ch := make(chan Event, 1024) // 关键消费者使用更大缓冲
    // ...
}
```

Orchestrator 和 ProjectionBuilder 使用 `SubscribeCritical`，TUI 使用普通 `Subscribe`。

## 七、纰漏 6：存储层缺事务

### 7.1 问题位置
- `internal/app/app.go:1192~1290` — `mcpPlanExpandToTasksTool`
- `internal/commands/command.go` — `Bus.Send` 单条执行
- `internal/store/db.go` — 无 `WithTx` 方法

### 7.2 会导致什么具体问题

**mcpPlanExpandToTasksTool 的执行流程**：

```go
for i, step := range steps {
    taskID := uuid.NewString()
    // 1. 创建 task
    m.cmdBus.Send(commands.CreateTask{...})
    
    // 2. 创建 dependency（如果非第一个 step）
    if i > 0 {
        m.cmdBus.Send(commands.CreateDependency{...})
    }
    
    // 3. 更新 plan step 关联
    m.cmdBus.Send(commands.UpdatePlanStep{...})
}
```

**每条 `cmdBus.Send` 独立执行 `db.Exec`**，没有事务包裹。

**后果场景**：
- Plan 有 5 个 step
- Step 1~3 成功创建 task 和 dependency
- Step 4 的 `CreateTask` 成功，但 `CreateDependency` 因为外键约束失败（上游 task 不存在——虽然在这个场景下不应该发生，但如果数据库并发修改了其他 task，可能触发）
- 结果：Plan 部分展开，task 1~4 存在，但 task 4 的 dependency 缺失
- 用户看到的 DAG 是"断开的"——task 4 显示为 active，但没有前置 dependency
- 更糟的情况：如果 step 3 的 `UpdatePlanStep` 失败，task 3 存在但 plan step 不关联，导致孤儿 task

**数据库层面**：
- SQLite 未设置 `PRAGMA busy_timeout`，并发写冲突时返回 `database is locked`
- 没有重试逻辑，直接失败
- 如果多个 goroutine 同时写（如 Agent 心跳 + TUI 状态更新），冲突概率增加

### 7.3 修复方案

**方案 A：commands.Bus 增加 SendTx（推荐）**

```go
// internal/commands/command.go

type Bus struct {
    store *store.Store
}

func (b *Bus) SendTx(cmds []Command) error {
    tx, err := b.store.DB().Begin()
    if err != nil {
        return err
    }
    defer tx.Rollback()
    
    for _, cmd := range cmds {
        if err := cmd.Execute(tx); err != nil {
            return err
        }
    }
    
    return tx.Commit()
}
```

> 需要所有 Command 的 `Execute` 方法接受 `*sql.Tx` 而非 `*sql.DB`。

**方案 B：Store 暴露 WithTx**

```go
func (s *Store) WithTx(fn func(*sql.Tx) error) error {
    tx, err := s.db.Begin()
    if err != nil {
        return err
    }
    defer tx.Rollback()
    
    if err := fn(tx); err != nil {
        return err
    }
    return tx.Commit()
}
```

**方案 C：SQLite 设置 busy_timeout**

```go
func newSQLiteStore(dbPath string) (*Store, error) {
    // ...
    if _, err := db.Exec("PRAGMA busy_timeout = 5000"); err != nil {
        db.Close()
        return nil, fmt.Errorf("set busy_timeout: %w", err)
    }
    // ...
}
```

> 这样写冲突时 SQLite 会自动重试 5 秒，而不是立即返回 `database is locked`。

**方案 D：限制 SQLite 连接数为 1（保守）**

```go
db.SetMaxOpenConns(1)
```

> 这样彻底避免并发写冲突，但牺牲并发读性能。对于桌面 TUI 应用，通常只有一个用户操作，所以这是可接受的。

## 八、纰漏 7：A2A 模块未按架构废弃

### 8.1 问题位置
- `internal/a2a/router.go`（整个目录）
- `docs/architecture/mcp-a2a-refactor-plan.md`

### 8.2 会导致什么具体问题

**（1）维护两套通信协议**

A2A（Agent-to-Agent）和 MCP（Model Context Protocol）功能重叠：
- A2A 提供 Unix Socket 消息路由
- MCP 提供 HTTP/Unix Socket tool/resource 调用

维护两套协议意味着：
- 每个新功能需要在两个协议中实现
- 两套 socket 可能冲突（如果路径相同）
- 测试工作量翻倍

**（2）ADR 与代码不同步**

架构文档 `mcp-a2a-refactor-plan.md` 明确建议废弃 A2A，但代码中 `internal/a2a/router.go` 仍有 252 行。新开发者可能：
- 阅读 ADR 后认为 A2A 已废弃
- 但看到代码后困惑："到底用哪个？"
- 可能误用 A2A 实现新功能，导致后续需要再次迁移

**（3）A2A 本身也有泄漏风险**

```go
func (r *Router) Start() error {
    listener, err := listenUnixSocket(r.socketPath)
    // ...
    go r.acceptLoop()  // 未展示完整代码，但大概率有与 MCP 类似的 accept loop
}
```

A2A 的 accept loop 很可能有与 MCP 相同的 goroutine 泄漏问题（未设置超时）。

### 8.3 修复方案

**方案 A：直接删除（如果确认无人使用）**

```bash
rm -rf internal/a2a/
```

然后删除所有引用：
```bash
grep -rn "a2a" internal/ cmd/
```

**方案 B：渐进式迁移（如果 A2A 有用户）**

1. 将 A2A 的心跳功能迁移为 MCP tool：
```go
// internal/mcp/tools.go
mcpServer.RegisterTool("agent_heartbeat", func(args map[string]any) (map[string]any, error) {
    sessionID := args["session_id"].(string)
    // 更新心跳时间
    return map[string]any{"status": "ok"}, nil
})
```

2. 标记 A2A 为 deprecated：
```go
package a2a

// Deprecated: Use MCP tools instead. This package will be removed in v0.3.
```

3. 在 v0.3 中删除。
